A visual, non-technical guide to the 7-phase journey from the current codebase to a clean, safe, and scalable backend.

Reading the arrows:

  • Phase 0 must finish first — it is the foundation for everything
  • Phases 1 → 2 → 3 are sequential — each one reshapes the code further
  • Phase 4 (visibility) can start as soon as Phase 0 is done, running alongside Phases 1–3
  • Phase 5 (speed) needs both Phase 3 and Phase 4 complete
  • Phase 6 (security) can start after Phase 0, benefits from Phase 4's logging

3. Phase-by-Phase Summary

Phase 0 — Build the Safety Net
Goal Make it safe to change anything without breaking the product
What happens We add automated tests that verify the system works correctly — covering patient referrals, billing, chat, and all critical workflows
What it unlocks Every future phase can proceed with confidence, because tests catch mistakes immediately
Business value Prevents costly bugs from reaching users during the refactoring process

Phase 1 — Clean Up the Code
Goal Make the existing code easier to work with
What happens We break up 6 massive files (some over 15,000 lines) into smaller, focused files. We remove dead code and improve naming
What it unlocks Developers can find, understand, and modify code faster
Business value Reduced development time for bug fixes and new features

Phase 2 — Organize by Business Domain
Goal Structure the code to match how the business actually works
What happens We reorganize code into clear areas: Clinical (referrals, evaluations), Users, Chat, Billing, Notifications, and Shared Tools
What it unlocks Teams can work on their domain without stepping on each other's toes
Business value Faster feature delivery with fewer cross-team blockers

Phase 3 — Decouple the Domains
Goal Make each business area independent so changes don't cascade
What happens We replace direct connections between domains with an event-based system. Instead of billing code reaching into user code, it sends a message that user code listens for
What it unlocks Each domain can be updated, tested, and deployed with minimal risk to others
Business value New features in one area no longer risk breaking another

Phase 4 — Make the System Visible
Goal Know what the system is doing at all times
What happens We add structured logging, request tracking, and monitoring for all 18 background jobs
What it unlocks When something goes wrong, we can trace the exact path and fix it quickly
Business value Faster incident resolution — minutes instead of hours

Phase 5 — Speed Things Up
Goal Make the platform faster based on real usage data
What happens We measure actual performance bottlenecks and fix them — optimizing database queries, adding caching for frequently accessed data
What it unlocks A measurably faster experience for all users
Business value Better user experience, lower infrastructure costs

Phase 6 — Lock Down Security
Goal Bring security up to industry standards
What happens We fix authentication, add rate limiting, harden configurations, and ensure all data queries are safe from injection attacks
What it unlocks Compliance with OWASP Top 10 security standards, A-grade security headers
Business value Protects patient data, reduces liability, builds trust with healthcare providers

7. Glossary

Terms used in this roadmap, explained in plain language:

Term What It Means
Safety net Automated tests that verify the system works correctly — if something breaks, we know immediately
God file A single file that has grown too large and does too many things, making it hard to work with
Domain A distinct area of the business (e.g., Clinical, Billing, Chat, Users)
Decoupling Making sure one part of the system doesn't directly depend on another, so changes stay contained
Domain events A messaging pattern where one area announces "something happened" and other areas react — instead of directly calling each other
Observability The ability to understand what the system is doing from the outside, through logs, traces, and metrics
OWASP Top 10 The industry-standard list of the 10 most critical web application security risks
CI pipeline An automated process that checks code quality and runs tests every time someone proposes a change
Contract tests Tests that verify the system's external behavior (what users and other systems see) hasn't changed
